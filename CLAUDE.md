# Hue Remote Scenes — project notes

A Home Assistant Marketplace (formerly HACS) custom integration, domain `hue_remote_scenes`, (renamed from `zha_scenes`/ZHA Scenes on 2026-11-18: that name clashed with marcelveldt/zha-scenes, a Hue preset/dynamic scenes project). It makes **Hue remotes recall scenes stored in the lamps** on ZHA, with no Hue Bridge: Tap Dial set-up (fixed group, button scene ids), scenes stored on the lights (store / recall / rename / delete / import) and a **remote → group binding** UI. Hue-first by design; other Zigbee lamps can share the groups. Built for Elliot's Hue lights and Hue Tap Dials, as part of moving from Z2M to ZHA. Sibling project: `hive-local` (same structure and conventions).

## Layout

- `custom_components/hue_remote_scenes/`
  - `__init__.py`: `async_setup` registers the static path, websocket commands and actions. `async_setup_entry` checks ZHA is running (else `ConfigEntryNotReady`), loads the store, sets `entry.runtime_data = SceneManager`, forwards the `scene` platform, registers the admin-only panel.
  - `config_flow.py`: one step, aborts if ZHA isn't loaded. `single_config_entry` in the manifest.
  - `zigbee.py`: all ZHA/zigpy access, via `homeassistant.components.zha.helpers.get_zha_gateway(hass)` → `.groups` (id → ZHA Group: `.name`, `.members` with `.device`/`.endpoint_id`/`.endpoint`, `.endpoint` = zigpy group endpoint) and `.devices` (EUI64 → ZHA Device: `.device` is zigpy).
  - `manager.py`: `SceneManager`, the operations shared by websocket, actions and entities.
  - `store.py`: scene names and member lists, plus each remote's remembered group bindings, in HA storage (`.storage/hue_remote_scenes`). Fires `SIGNAL_SCENES` on change. On first start with no store of its own, it imports the pre-rename `.storage/zha_scenes` (`LEGACY_STORAGE_KEY`).
  - `areas.py`: HA areas (and `area_icons`, sent with groups and remotes). A group's area is the area set on ZHA's group entity (`light_zha_group_0x<id>`, platform `zha`, owned by the coordinator), otherwise its members' device areas. Devices are looked up by identifier `("zha", str(ieee))`.
  - `scene.py`: one `scene` entity per stored scene, added and removed as the store changes. Unique id `<group>_<scene>`.
  - `websocket.py`: `hue_remote_scenes/groups|subscribe|store|recall|copy|rename|delete|import|remotes|bindings|bind|find_dial_group|lights|create_group|set_cycle`.
  - `services.py`: `store_scene`, `import_scenes` (both return a response). Recall is `scene.turn_on`.
  - `logic.py`: pure helpers (no HA or zigpy imports), unit-tested in `tests/`.
  - `frontend/hue-remote-scenes-panel.js`: **built artifact**. Don't edit it. Run `npm run build` in `/frontend`.
- `frontend/src/`: React 18 panel. Base CSS from hive-local (`.card`, `.chip`, `.chip-btn`, `.segmented`, `.status`, header and tabs) plus a Hue-app-inspired layer (patterns only, no Hue branding). Two tabs: **Rooms** (`Rooms.tsx`: a card per HA area tinted with its lights' live colours via `model.roomBackground`, with `LightControls.tsx` `Switch` + `Brightness` on ZHA's group light entities → `RoomPage.tsx`: coloured hero, scene tiles from `Tiles.tsx` (`SceneTile` with ⋮ menu: edit, save over, rename, delete, on remote-button tiles too; `AddTile`), `SceneEditor.tsx` (new scene / edit: a sheet with per-light and all-lights on/off, brightness, white and colour presets and a colour picker, sent live via `light.turn_on` to the lights that support them, then `store` saves the lights' state; editing recalls the scene first and Cancel recalls it again), lights list, the room's remotes) and **Remotes** (`RemotesTab.tsx`: remotes by room, each section headed with the room's live colours, rows with what the remote does and its button scenes' swatches → `RemotePage.tsx`: per-button scene picker (copy, save current state, or clear), `Bindings` for plain remotes, `CycleSection.tsx`, and `DialSetup.tsx` (the 4-step set-up card, segmented step bar) until a dial is set up). `model.ts` holds pure helpers (areas, remote status, dial progress, swatch colours and `isPale`, room colour/brightness, friendly model names). `main.tsx` re-renders at most once a second on `hass` changes for live state. `RemoteIcon.tsx` draws outline icons for the Hue remotes we know (Tap Dial, dimmer, smart button), MDI otherwise. `Logo.tsx` is the brand mark.
- `entities.py`: HA entities of ZHA devices: a group's light entity (`light_zha_group_0x<id>`, sent as `groups[].entity_id`), a member's light entity, a remote's battery sensor, and `scene_colors` (the members' `rgb_color` + brightness when a scene is saved, stored as the scene's `colors` for the panel's swatches; None = off).
- `docs/`: README screenshots (light and dark), rendered from the built panel bundle with mock data in headless Chromium, framed on a brand-gradient background.
- `tests_ha/`: end-to-end tests with `pytest-homeassistant-custom-component` (HA 2026.2.3, zha 0.0.90). Real zigpy `Device`s and a zigpy `Groups`, a fake radio that decodes every frame and answers like real bulbs/remotes, and a fake ZHA gateway. Not run in CI (CI only installs `pytest`).

## Key facts (zigpy 0.92 / zha 0.0.90)

- zigpy Scenes commands are `store`, `recall`, `remove`, `get_scene_membership` (not `store_scene` etc.). Responses carry `status`; `get_scene_membership_response.scenes` is the id list.
- **Store / remove / membership are unicast to each member** with a Scenes server cluster: devices don't answer group-addressed scene commands, and we want per-light results. **Recall is one groupcast** (`group.endpoint[0x0005].recall(...)`; Scenes is in zigpy's group-cluster registry), so the lights change together, like a bound remote.
- `transition_time` is in tenths of a second. After a recall we re-read on/off, level and colour attributes (`REFRESH_DELAY` + transition) so ZHA's light entities update. ZHA's cluster handlers listen for `attribute_read` events.
- Store requires the light to already be a member of the group, which ZHA's group management does.
- **Copy scene** (`zigbee.async_copy`, ZCL Scenes 0x42, `hue_remote_scenes/copy`) is unicast like store: each light copies a stored scene to another id without changing, so the panel can put an existing scene on a remote button. Unverified on real Hue bulbs.
- Remove returning `NOT_FOUND` just means that light never had the scene; it isn't treated as a failure.
- Bindings: we send ZDO `Bind_req`/`Unbind_req` ourselves (`MultiAddress(addrmode=1, nwk=group_id)`), one cluster at a time, because ZHA's `async_bind_to_group` only logs failures. The binding table is read with `Mgmt_Bind_req`, paged by `StartIndex`.
- **Remembered bindings:** the binding table lives on the (usually asleep) remote, so we keep `{ieee: {groups: {gid: [clusters]}, checked}}`. Bind/unbind results update it (`logic.apply_bind_results`), and a table read replaces it and sets `checked`. Group cards show the remotes bound to them from this, without waking anything. Bindings made elsewhere only show up after **Check bindings**.
- **Bind clears leftovers:** the panel binds with `exclusive: true`. Once the bind succeeds (the remote is awake), we read the table and unbind everything except the target group, the remote's dial group (if set up: its scene buttons only recall there) and the coordinator (`logic.stale_bindings`): other groups (Z2M, earlier binds) and direct device bindings (e.g. to a bulb). Coordinator bindings stay, because ZHA's `zha_event`s and the dial's group finder use them. `NO_ENTRY` on unbind counts as removed. The table read also refreshes the remembered bindings and `checked`.
- **Hue Tap Dial (RDM002) scene buttons:** with its Scenes cluster bound to a group, the dial recalls scenes **1, 0, 5, 4** (buttons 1–4, `logic.DIAL_BUTTONS`) on its **own fixed group id**, directly over Zigbee. Holding a button turns the lights off, and the dial dims (Z2M RDM002 docs). The buttons' Hue-specific `0xFC00` events also reach the coordinator, but that isn't the scene path.
  - `zigbee.async_find_dial_group` binds the dial's Scenes **out** cluster to the coordinator (ZDO Bind_req, addrmode 3, coordinator endpoint 1), retrying every `BIND_RETRY` s while it sleeps, then waits for a recall (`cluster_command` 0x05 on that out cluster) and reads `group_id`. The coordinator binding is left in place (harmless).
  - `zigbee.async_create_group` uses ZHA's `gateway.async_create_zigpy_group(name, members, group_id)` (needs a unique name) or `group.async_add_members`.
  - The store keeps `remotes[ieee]["dial"] = {group_id, buttons}`. `SceneManager.async_store(scene_id=…, name=…)` creates a scene at a fixed id, and new scenes in a dial's group skip the button ids.
  - Panel: the set-up view (`DialSetup.tsx`: find → choose lights → bind → save button scenes), and button rows in the group's card in its area. The Remotes tab works with no groups (Elliot re-paired everything).
- **Hue dimmer switches** (researched Nov 2026, nothing confirmed on hardware yet):
  - **RWL022 (gen 2):** one endpoint, out clusters `[0x19, 0, 3, 4, 6, 8, 5, 0x1000]` (zhaquirks `rwl022.py` signature). Z2M docs (929002398602): when bound, power alternates On/OffWithEffect, up/down send Step, and the **Hue button sends RecallScene on a fixed per-remote group, alternating scenes 0 and 1** (Z2M exposes `recall_0`/`recall_1`; zha-device-handlers#4747 logs a Recall group 0x2A2A scene 0). So it reuses the dial flow: `DIAL_BUTTONS["RWL022"] = Hue button A (0), B (1)`. Which comes first is unverified. The Z2M page's own text says "scenes 1 and 2" in one place and "0 and 1" in another; we go with 0/1.
  - **RWL020/RWL021 (gen 1):** endpoint 1 is ZLL profile, out `[0, 3, 4, 6, 8]` on old firmware and `+5` (Scenes) on newer; endpoint 2 has `0xFC00` (zhaquirks `rwlfirstgen.py`). Z2M docs: bound, On sends On, Off sends OffWithEffect, up/down Step/Stop. No scene recall documented. So: buttons stay bound to the group, and **HA cycles scenes** (`logic.CYCLE_TRIGGERS`): `zha_event` with `command` `on_press` → `SceneManager.async_cycle` groupcasts the next scene in `remotes[ieee]["cycle"] = {group_id, scene_ids}`. Restarts from the first after `CYCLE_RESET` s. Position is runtime-only.
  - **ROM001 / RDM003 (smart button):** same descriptor as RWL022, but Z2M documents only on/off (alternating) and step; no recall. Cycle trigger is `on_double_press` because a single press toggles.
  - Hue remote presses reach HA as `zha_event` from the `0xFC00` quirk cluster (`PhilipsRemoteCluster`: commands `<button>_press`, `_short_release`, `_double_press`, `_hold`, `_long_release`; buttons `on`/`up`/`down`/`off`). `_press` comes ~300 ms after release (multi-press detection). ZHA binds `0xFC00` to the coordinator; HA 2026.2.0/2026.2.1 didn't (zha-device-handlers#4747, fixed in zha 0.0.90 / HA 2026.2.2; reconfigure affected remotes).
- Remote detection: a non-ZDO endpoint with on/off, level or scenes **client** (out) clusters and no on/off server cluster.
- **ZHA hands out zigpy `t.Group` ids**, an int that `str()`s as `"0x0005"` but goes over JSON as `5`. Always `int()` them: `zigbee.groups()` does, and `store._key()` uses `str(int(id))`. Mixing the two hid every saved scene from the panel. The e2e fake uses real `t.Group` ids to catch this.
- Scene ids are allocated from 1 (0 is often a remote's default). Names are ours; the lights only store ids.
- Community report (HA forum, Hue Tap Dial + ZHA): someone failed to store scenes on Hue bulbs via `zha.issue_zigbee_cluster_command` and ZHA Toolkit. Possibly a usage problem, but **unverified on real Hue bulbs**.

## Conventions

- **Shipping an update:** bump `version` in `manifest.json` (semver), push to main, then run the **Release** workflow (`.github/workflows/release.yml`, `workflow_dispatch` with a `notes` input) on main: it tags `v<version>` and publishes the release. From a cloud session, start it with the GitHub tools' `actions_run_trigger` (tag pushes and `gh release` are blocked there). Locally, `gh release create vX.Y.Z --target main` with short notes also works. The Marketplace (formerly HACS) offers updates from GitHub releases; without a new release, **Update** stays greyed out and users can only Redownload.
- Python: HA style, type hints, `from __future__ import annotations`. Keep `logic.py` free of HA and zigpy imports.
- Run `pytest -q tests`, the `tests_ha` suite and `cd frontend && npm run build` before committing, and commit the rebuilt bundle.
